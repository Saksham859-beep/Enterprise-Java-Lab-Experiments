# Experiment 8: REST API Testing with cURL and Automated Tests

## Aim

Test the REST API by sending HTTP requests from the command line with cURL, check the CRUD operations against MySQL, read the HTTP status codes, and write the first automated tests with Spring Boot and JUnit.

## Learning outcomes

1. Understand what an API testing tool does.
2. Send GET, POST, PUT and DELETE requests with cURL.
3. Send JSON to REST endpoints.
4. Test CRUD operations connected to MySQL.
5. Read HTTP status codes.
6. Confirm in the database that records were created, updated or deleted.
7. Run basic automated API tests with Spring Boot, JUnit and MockMvc.

## HTTP methods and status codes

| Method | Purpose | CRUD operation |
| --- | --- | --- |
| GET | Retrieve data | Read |
| POST | Create a record | Create |
| PUT | Update a record | Update |
| DELETE | Delete a record | Delete |

| Code | Meaning | Where it appears in this project |
| --- | --- | --- |
| 200 | OK | Successful GET, POST, PUT and DELETE |
| 201 | Created | Not used; this API answers creation with 200, as the lab does |
| 400 | Bad Request | Validation failure (Experiment 7) |
| 401 | Unauthorized | Missing or wrong credentials (Experiment 9) |
| 404 | Not Found | Student id that does not exist |
| 500 | Internal Server Error | Unexpected server-side failure |

## Part 1: Database correction

While testing, the `students.id` column turned out to have been created without `AUTO_INCREMENT`, because the entity had no `@GeneratedValue` when the table was first created in Experiment 4. `ddl-auto=update` adds missing columns but does not alter the definition of an existing one, so the table had to be fixed by hand. The whole script is in `sql/03-exp8-auto-increment-fix.sql`.

```sql
USE studentdb;
SHOW TABLES;
DESCRIBE students;
SHOW CREATE TABLE course;
```

The foreign key from `course` to `students` blocks changes to the referenced column, so it is dropped first. The constraint name is generated by Hibernate and can differ between machines, which is why `SHOW CREATE TABLE course;` is run first to read the real one.

```sql
ALTER TABLE course DROP FOREIGN KEY FKk8cjbc26apsiim9kt00ryasi1;

ALTER TABLE students
    MODIFY COLUMN id INT NOT NULL AUTO_INCREMENT;

ALTER TABLE course
    ADD CONSTRAINT FKk8cjbc26apsiim9kt00ryasi1
    FOREIGN KEY (student_id) REFERENCES students(id);
```

Verify:

```sql
DESCRIBE students;
DESCRIBE course;
```

`id` must show `auto_increment` in the `Extra` column, and `course` must still have `student_id`.

This was a one-time correction. It is only needed for a database created before `@GeneratedValue` existed. On a brand-new `studentdb`, Hibernate builds the table with `AUTO_INCREMENT` straight away because the final entity already has the annotation, so the script can be skipped.

## Part 2: Student.java corrections

| Before | After |
| --- | --- |
| `private int id;` | `private Integer id;` with `@GeneratedValue(strategy = GenerationType.IDENTITY)` |
| `import ...Positive` and `@Positive` on `id` | Removed |
| `public Student(int id, String name, String email)` | `public Student(String name, String email)` plus the empty constructor |
| `int getId()` and `setId(int id)` | `Integer getId()` and `setId(Integer id)` |
| `new Student(1, "Rahul", "rahul@example.com")` in the controller | `new Student("Rahul", "rahul@example.com")` |

Why `Integer` instead of `int`: a primitive `int` always has a value, so a new object has id 0 and cannot show it is unsaved. An `Integer` is `null` until the database assigns an id, which is what lets JPA tell a new student from an existing one.

The lab sheet shows `@NotBlank` and `@Email` without messages in this step. The repository keeps the messages from Experiment 7, because the automated test below asserts the exact texts `Student name is required` and `Please provide a valid email address`.

## Part 3: cURL test run

Run from Command Prompt with the application started. These are the original lab commands. In the final application add `-u admin:admin123` to each, since Experiment 9 protects every endpoint except `/hello`.

| Step | Command | What to verify |
| --- | --- | --- |
| 1. List all | `curl -i http://localhost:8081/students` | 200 and the records as JSON |
| 2. Get one | `curl -i http://localhost:8081/students/1` | Details of student 1 |
| 3. Create | `curl -i -X POST http://localhost:8081/students -H "Content-Type: application/json" -d "{\"name\":\"Karan Verma\",\"email\":\"karan@example.com\"}"` | 200 and a generated id |
| 4. Check it | `curl -i http://localhost:8081/students/11` | The new student (use the id from step 3) |
| 5. Update | `curl -i -X PUT http://localhost:8081/students/11 -H "Content-Type: application/json" -d "{\"name\":\"Karan Sharma\",\"email\":\"karan.sharma@example.com\"}"` | New name and email |
| 6. Check it | `curl -i http://localhost:8081/students/11` | Updated details |
| 7. Delete | `curl -i -X DELETE http://localhost:8081/students/11` | `Student deleted successfully` |
| 8. Check it | `curl -i http://localhost:8081/students/11` | `HTTP/1.1 404` |

The id 11 in the lab was simply the next value MySQL generated on that machine. Yours depends on what is already in the table, so use whatever id step 3 returns.

`scripts/exp03-04-crud.sh` does all eight steps in one run and reads the generated id from the response, so it does not depend on a fixed number.

## Part 4: Automated tests

Tests live in `student-management/src/test/java/com/example/ucs067/studentmanagement/`.

`StudentManagementApplicationTests` is the test class from the lab sheet:

| Test | Checks |
| --- | --- |
| `contextLoads` | The Spring context, security, JPA and the database all start |
| `helloEndpointReturnsMessage` | `GET /hello` returns 200 and `Hello, Spring Boot!` |
| `invalidStudentDataReturnsBadRequest` | `POST /students` with a blank name and a bad email returns 400 with both messages |

It uses `@SpringBootTest`, `@AutoConfigureMockMvc` (from `org.springframework.boot.webmvc.test.autoconfigure` in Spring Boot 4) and `MockMvc`, which sends requests through the whole Spring MVC stack without opening a real network port.

Two adjustments were needed because the project later gained Spring Security:

- The invalid-data test sends an HTTP Basic header for `admin:admin123`, otherwise the request would be stopped with 401 before validation ever ran.
- The tests run with the `test` profile.

More test classes cover the rest of the API:

| Class | Covers |
| --- | --- |
| `StudentCrudApiTests` | Create, read all, read one, update, delete and every 404 case |
| `StudentQueryApiTests` | Derived queries, pagination and sorting (Experiment 5) |
| `CourseRelationshipApiTests` | Courses per student, the course list, an unknown student, cascade delete (Experiment 6) |
| `ValidationApiTests` | Rejected create and update, unchanged record after a failed update (Experiment 7) |
| `SecurityApiTests` | Public `/hello`, 401 without or with wrong credentials, 200 with the right ones (Experiment 9) |

### The test profile

`src/test/resources/application-test.properties` points the tests at an in-memory H2 database:

```
spring.datasource.url=jdbc:h2:mem:studentdb;DB_CLOSE_DELAY=-1
spring.datasource.username=sa
spring.datasource.password=
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.show-sql=false
```

This way `mvn test` runs on any machine, including one with no MySQL installed, and never touches the real `studentdb` data. Every test class empties the tables before each test so that tests do not depend on each other. To run the tests against MySQL instead, remove `@ActiveProfiles("test")` from the test classes.

### Running them

```
cd student-management
mvn test
```

Reports are written to `student-management/target/surefire-reports/`.

## Concepts learned

- cURL is enough to exercise every endpoint from the command line.
- Status codes are part of the API contract and should be verified, not only the body.
- The database should be checked directly to prove that an API call really changed the data.
- `ddl-auto=update` does not alter existing column definitions, so some schema changes need SQL.
- Wrapper type `Integer` is the right choice for a generated primary key.
- `MockMvc` allows quick, repeatable controller tests that run with `mvn test`.
